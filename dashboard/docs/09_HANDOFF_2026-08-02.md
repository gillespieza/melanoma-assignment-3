## The phenotype bug — full context, so it doesn't need re-discovering

Original bug: `q5-patient-stratification`'s K-Means cluster labeling
hardcoded index→name (`0: "Mutant-Driven", 1: "Immune Cold"...`), but K-Means
cluster indices are arbitrary per run — this mislabeled all three non-cold
clusters (verified by recomputing feature means directly: the cluster
labeled "Mutant-Driven (NF1 Loss)" had 0% NF1 mutations; the actual 100%-NF1
cluster was labeled "M2 Immunosuppressive"; "Immune Hot" had the *lowest*
TIS/CYT/CD8 of all four clusters).

Amanda fixed the index-hardcoding (`fecda91`, `5994f8c`) with a rank-based
`assign_phenotype_labels()` — NF1/Hot/Cold direction all verified correct
after that fix. **But a second, different bug was found afterward**: her own
function docstring says Rule 3 should assign "M2 Immunosuppressive" by
lowest M1/M2 macrophage ratio, but the actual code doesn't implement that —
it assigns "Immune Cold" by lowest TIS instead, leaving M2 Immunosuppressive
as an unverified leftover bucket. Re-verified against her latest push
(699-patient version): the "M2 Immunosuppressive" cluster had *below-average*
M2 macrophage levels and a *less* M2-skewed ratio than the cluster labeled
"Immune Cold" — i.e., those two labels are arguably still swapped, just via a
different mechanism.

She's now done a further rewrite (`tweak-dashboard`'s "Two-Stage GMM
phenotyping") — **this may or may not have fixed it. Don't assume either
way — check the actual current code and recompute the numbers, same method
as above.**
